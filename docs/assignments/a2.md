## Why this assignment

Two reasons, and the first one is the important one.

**You will hit this at work.** Committing straight to `main` in a shared repository
and then needing the upstream history back is one of the most common situations in
professional git — and one of the most commonly botched. Doing it once, deliberately,
with an instructor available, is worth more than reading about it. Nothing here
destroys your work; every step is reversible, and the assignment says why.

**And you cannot exercise what you have not seen.** The API roughly doubled in
surface since Assignment 1. Walking it once, endpoint by endpoint, is what makes the
next sessions hands-on rather than spent finding out where things are.

## Learning outcomes

By the end you will be able to:

- Move commits off `main` onto a branch of your own, and reset `main` to match
  upstream — explaining *why* nothing was lost.
- Bring your repository up to date and merge upstream changes into your own branch,
  resolving conflicts if they appear.
- Run the current stack both in Docker and directly on your machine, and say what
  the difference means for authentication.
- Exercise every endpoint from Postman, and read what each response is telling you.

## Part 1 — Get your repository back in step

Work through this in order. **Read each step before running it** — step 1 exists so
you know which case you are in.

### 1. Find out where you actually are

```bash
git status                     # uncommitted changes? which branch?
git branch -vv                 # your branches, and what they track
git log --oneline --graph -10  # your last ten commits
git fetch origin               # get the latest upstream refs (changes nothing local)
git log --oneline origin/main -3
```

Now compare: does your `main` contain commits that `origin/main` does not?

```bash
git log --oneline origin/main..main    # YOUR commits that upstream does not have
```

- Output is **empty** and `git status` is clean → you are in **Case C**, skip to
  step 4.
- Output **lists commits** → **Case A**.
- Output is empty but `git status` shows modified files → **Case B**.

### 2. Case A — you committed your work on `main`

Your commits are safe. A branch in git is only a *pointer to a commit*, so creating
one at your current position keeps everything, and resetting `main` afterwards moves
only `main`'s pointer — it does not delete commits.

```bash
# 1 · create a branch HERE, at your current commit — your work now has a name
git switch -c my-work

# 2 · confirm your commits are on it
git log --oneline -5

# 3 · go back to main and make it match the course repo exactly
git switch main
git fetch origin
git reset --hard origin/main

# 4 · verify: main is now identical to upstream, and your work still exists
git log --oneline -3
git log --oneline my-work -3
```

> `git reset --hard` discards **uncommitted** changes in the working tree. That is
> why step 1 comes first: once your work is committed on `my-work`, there is nothing
> left to lose. If you are nervous, run `git branch backup-main` before the reset —
> a second pointer costs nothing.

### 3. Case B — you have uncommitted changes on `main`

Commit them onto a branch first, then reset `main`:

```bash
git switch -c my-work
git add -A
git commit -m "My work from sessions 1-4"

git switch main
git fetch origin
git reset --hard origin/main
```

If you would rather not commit half-finished work, `git stash` is the alternative:

```bash
git stash push -m "wip"        # set the changes aside
git switch main
git fetch origin
git reset --hard origin/main
git switch -c my-work
git stash pop                  # bring them back on your own branch
```

### 4. Pull the latest `main`

```bash
git switch main
git pull --ff-only origin main
```

`--ff-only` refuses to create a merge commit: if it fails, your `main` still has
local commits and you should go back to step 2. Confirm you are current:

```bash
git log --oneline -1           # should match origin/main
git status                     # should say "up to date" and "nothing to commit"
```

You should now see the new folders: `code/frontend/`, `code/backend/examples/`,
`code/backend/scripts/`, and `code/backend/app/agents/`.

### 5. Optional — bring the new code into your own branch

Only if you want to keep building on top of your work:

```bash
git switch my-work
git merge main
```

If git reports conflicts, it is telling you that you and the course repo changed the
same lines — it is not an error. Open each marked file, decide what the final content
should be, then:

```bash
git add <the files you fixed>
git commit                     # completes the merge
```

To abandon the attempt and return to where you were: `git merge --abort`.

> **Why merge and not rebase?** Your branch may already be pushed, and rebasing
> rewrites commits — see the worked example with hashes and timestamps in
> [How git works](../topics/ref-git.html#merging).

### Part 1 acceptance

### 2. Start it — Docker

```bash

```

Three containers now, not two: the API (**7799**), Qdrant (**7833**) and the new
**console** (**7800**).

| Open | What it is |
|---|---|
| <http://localhost:7800> | The console — a screen per part of the pipeline |
| <http://localhost:7799/docs> | Swagger — still the debugging surface |
| <http://localhost:7833/dashboard> | The Qdrant dashboard |

### 3. Walk the console

Click through every screen and note what each one shows you:

| Screen | Do this | Notice |
|---|---|---|
| **Status** | Read the Azure panel | Resource, region, both endpoints, and the **authentication lane** |
| **Knowledge** | Paste the sample text, preview all four strategies, then ingest | The boundaries move per strategy; the vector dimension after ingest |
| **Retrieval** | Try "my card got frozen" and then an off-topic question | Scores collapse when nothing matches |
| **Chat** | Ask the same question as `default`, then as `lyrical` | Same facts, same citations, different voice — open *the exact prompt that was sent* |
| **Agents** | Read the badges | Where each agent can run: local only, local + Foundry, Foundry only, or unknown |
| **Tools** | Fetch `https://example.com`, then a real documentation page | The `warnings` list on the second one |

**Expect "Foundry: unknown" in Docker.** The Agent Service accepts only Microsoft
Entra authentication and the container uses a key, so the honest answer is
*unknown* rather than "not deployed". Which brings us to the second run mode.

### 4. Start it — locally, without Docker

This is the mode where the Azure surface is visible, because the app can borrow your
`az login`.

```bash
# terminal 1 — the API
cd code/backend
docker compose down                # stop the containerised stack first
docker compose up qdrant -d        # keep only the vector database
uv sync                            # first time only
az login
uv run uvicorn app.main:app --reload --port 7799

# terminal 2 — the console
cd code/frontend
npm install                        # first time only
npm run dev                        # http://localhost:7800
```

Open **Agents** again. The badges now resolve to *local only* and *local + Foundry*,
and **Status → Azure** lists your real model deployments. Same code, different
authentication — that is the whole lesson.

> **Don't have `uv`, or `uv run` fails?** Install it in PowerShell with
> `powershell -ExecutionPolicy ByPass -c "irm https://astral.sh/uv/install.ps1 | iex"`,
> then **open a new terminal** (a terminal only reads `PATH` when it starts — this is
> the single most common failure).
>
> Or skip `uv` entirely and use a plain virtual environment:
>
> ```powershell
> cd code\backend
> py -3.12 -m venv .venv
> .\.venv\Scripts\Activate.ps1
> pip install -r requirements.txt
> uvicorn app.main:app --reload --port 7799
> ```
>
> `requirements.txt` is generated from `uv.lock`, so both paths install identical
> versions. The full table of setup problems and fixes is in the
> [backend README](../../code/backend/README.md#python-setup-on-windows--uv-or-a-plain-virtual-environment).

## Part 3 — Walk the Postman collection, folder by folder

Import [`code/backend/postman/rag-teaching-api.postman_collection.json`](../../code/backend/postman/rag-teaching-api.postman_collection.json)
(Postman → *Import* → drop the file). It has **28 requests in 7 folders** and is
meant to be run **top to bottom** — later folders depend on earlier ones.

Set the collection variable `baseUrl` to `http://localhost:7799` if it is not already.

### 0 · Ops

| Send | Look for |
|---|---|
| `Health` | `status: ok`, `qdrant: ok`, and the agents block listing your personas |
| `Config (sanitized)` | Your settings with the key **masked** — the API never returns secrets |
| `Azure environment` | Resource, region, endpoints, auth lane. Under Docker the deployment list says why it is unavailable |

### 1 · Chunking — the same text, four strategies

Send all four. Nothing is stored — this is the chunking lesson on its own.

- **static** — fixed windows; look for a chunk that ends mid-sentence.
- **sentence** — clean boundaries, uneven sizes.
- **dynamic** — packs whole sentences to a size budget; no broken sentences.
- **semantic** — splits where meaning shifts. Slower: it embeds every sentence.

**Write down** how many chunks each produced from identical input.

### 2 · Ingestion

| Send | Look for |
|---|---|
| `Ingest sample text` | `count`, `vector_dimension` (1536), and `embedding_preview` — the first eight numbers of a real embedding |
| `Collection info` | `points_count` matching what you just ingested |
| `Reset collection` | **Don't send this yet** — folders 3 and 4 need the data |

### 3 · Retrieval

| Send | Look for |
|---|---|
| `card blocked (paraphrase)` | It finds the right chunk although the query says *frozen* and the text says *blocked* — no shared keyword |
| `early repayment` | Scores near the top |
| `off-topic` | Scores collapse. **This is the important one**: retrieval always returns something, so the score is what tells you whether it means anything |

### 4 · Generation — the RAG difference

| Send | Look for |
|---|---|
| `WITHOUT rag` | A fluent, plausible, unsupported answer — and a short `prompt_sent` |
| `WITH rag` | A grounded answer with `[1]` `[2]` citations — and a much longer `prompt_sent` containing the retrieved passages |
| `answer not in corpus` | It should **refuse** rather than invent |

Compare the two `prompt_sent` values side by side. That difference *is* RAG.

### 5 · Agents — where each one runs

| Send | Look for |
|---|---|
| `List agents` | `runs_on` per agent, and the `foundry` block saying whether the Agent Service could be queried at all |
| `One persona + its system prompt` | The exact system prompt the JSON produces, grounded and plain |
| `Ask · default` then `Ask · lyrical` | Same facts, same citations, completely different voice |

Now **edit `code/backend/app/agents/personas/lyrical.json`** — change a style rule —
save, and send `Ask · lyrical` again. It changes with no restart. That is the point
of the whole design: behaviour is data, not code.

The remaining three requests need a **Microsoft Entra identity**. The simplest way to
have one is to run the backend locally after `az login`; under Docker the default is
key auth, so they fail there until the container is given a service principal (see the
[backend README](../../code/backend/README.md#identity-inside-a-container)):

| Send | Look for |
|---|---|
| `Deploy a persona to Foundry` | An `agent_id`. Then re-send `List agents` — `lyrical` flips to `runs_on: both` |
| `Hosted agents` | What actually exists in your Foundry project |
| `Ask · run it in Foundry` | The same persona, `agent.mode: "foundry"` — executed by Azure, not by your process |

### 6 · Tools

| Send | Look for |
|---|---|
| `Web fetch · simple page` | Clean text, no warnings |
| `Web fetch · a real site` | The `warnings` array and `stats.signal_ratio` — everything the naive scraper could not handle |
| `Text to speech` | Needs an Azure Speech resource. Use Postman's **Send and Download** to save the WAV |
| `Speech to text` | Upload the WAV you just saved and read your own sentence back |

Finish by sending `Reset collection` from folder 2 to leave a clean slate.

## Troubleshooting

| Symptom | Fix |
|---|---|
| `git pull --ff-only` fails: "not possible to fast-forward" | Your `main` has local commits — go back to Part 1, step 2 |
| You reset and think you lost work | `git reflog` lists every position `HEAD` has held; `git reset --hard HEAD@{n}` returns you there. Almost nothing in git is truly gone for 30 days |
| Merge conflicts you cannot untangle | `git merge --abort` puts everything back; ask before trying again |
| Console shows "backend offline" | The API is not running, or you started the local backend while the container still holds port 7799 |
| Agents all show "Foundry: unknown" | Expected under Docker's default key auth. Run the backend locally after `az login`, or give the container a service principal |
| `Deploy a persona` returns 503 | Same cause — the Agent Service accepts only Entra authentication, never a key |
| The Foundry option is greyed out in Chat | That agent is not deployed. Deploy it from the Agents view, then reload |
| `Text to speech` returns 503 | No Azure Speech resource configured; set `AZURE_SPEECH_KEY` and `AZURE_SPEECH_REGION`, or skip those two requests |
| Port already in use | Something else is on 7799/7800/7833 — stop it, or change the ports in `.env` and `docker-compose.yml` |

## Tools worth installing

Optional, but each one is genuinely useful beyond this course.

- **[Podman](https://podman.io/)** — a drop-in alternative to Docker that runs
  containers without a background daemon and without root. `podman compose` accepts
  the same compose file. Worth knowing because many corporate environments,
  banks included, have moved to it for exactly those two reasons.
- **[llama.cpp](https://github.com/ggml-org/llama.cpp)** — runs open-weight models
  directly on your own CPU or GPU, in C++, with no Python and no service. It is the
  engine behind most local-model tooling (LM Studio and Ollama included). Clone it,
  build it, run a small model, and the "third lane" from Session 2 stops being
  theoretical.
- **[OpenCode](https://opencode.ai/)** — an open-source terminal coding agent. A good
  way to compare AI-assisted development tools against the ones we use in class, and
  to see the same spec-driven workflow in a different implementation.
