What a CLI and an SDK actually are — and why we install them

Beginners reasonably ask a sharp question: if the Azure portal can create everything, and an API key is a single line in a file, why does this course insist on installing a command-line tool and a software development kit? The answer is not preference or professional habit. It follows from what these three things actually are, and they are not three products — they are three clients of the same system.

One system, three ways in

Underneath everything, Azure is a collection of REST APIs: web services that accept HTTP requests carrying JSON and return JSON. Creating a resource group is an HTTP PUT. Listing your deployments is an HTTP GET. Asking a model a question is an HTTP POST. Nothing you can do in Azure exists outside this surface — the API is the product, and everything else is a way of producing those HTTP calls without composing them by hand.

The portal (portal.azure.com) is a website that turns clicks into those calls. The CLI — the command-line interface, invoked as az — is a program you install locally that turns typed commands into the same calls. The SDK — the software development kit, in our case the Python packages azure-ai-inference and azure-identity — is a library your own program imports so that your code can make those calls as ordinary function calls, without you writing HTTP plumbing, retries or token handling.

Control plane and data plane — the distinction that explains everything else

Notice that the diagram forks at the bottom, and the fork matters more than any other idea today. Azure Resource Manager (ARM) is the control plane: one uniform API for managing resources — creating a Foundry account, listing resource groups, assigning a role, reading a bill. It is identical in shape for every Azure service on earth, which is why one az command set can drive all of them.

The data plane is something else entirely: the endpoint of an individual service, doing that service's actual work. Your Foundry resource's …services.ai.azure.com endpoint answers chat completions and produces embeddings. An Azure AI Search service has its own endpoint that indexes and retrieves. A storage account has its own that reads and writes blobs. These endpoints have nothing in common with ARM and nothing in common with each other except the way they authenticate. Creating a model deployment is control plane; using it is data plane — and, as we will see in the wiring section, they do not share credentials.

Why not just use the website?

Because a click is an event and a command is an artifact. When you create a resource in the portal, the knowledge of how it was made lives in your memory and nowhere else — and memory does not survive a colleague, a second environment or six months. The same work expressed as commands becomes a file: it can be read, reviewed, corrected, committed to git, run again identically for a test environment, and executed by an automated pipeline at three in the morning when nobody is awake to click. Four specific properties follow, and every one of them is a professional requirement rather than a nicety:

PropertyWhat it meansWhy it matters in a bank
ReproducibilityThe same commands produce the same environment every timeDevelopment, test and production stop drifting apart — the classic source of "it worked in test"
ReviewabilityInfrastructure changes arrive as text a colleague can read before they happenFour-eyes principle applies to infrastructure, not only to application code
AutomationA pipeline can run it without a human presentDeployments happen on a schedule, unattended, identically
AuditabilityThe record of what was intended sits in version control next to who approved itRegulators ask "who changed what, when, and on whose authority" — and expect an answer

None of this makes the portal wrong. The portal is superb for exploring an unfamiliar service, inspecting state, reading metrics and diagnosing an incident visually. The professional pattern is to explore in the portal and then express the result as commands — discover by clicking, deliver by scripting.

Why not just use an API key?

This is the deeper question, and the answer is where cloud security actually lives. An API key is a long string that grants whoever holds it the full data-plane rights of a resource. It is a bearer secret: the service does not care who you are, only that you presented the string. That single property produces every one of its weaknesses.

A key does not expire on its own, so a copy taken today still works next year. It carries no identity, so the audit log records that "a key" called the model, not that you did — and when a team of eight shares one key, an investigation has nowhere to go. It has no granularity: there is no such thing as a read-only key or a key limited to one deployment. It cannot be constrained by the organization's other controls — no multi-factor authentication, no device compliance, no location policy applies to a string. And keys travel: into a chat message, a screenshot, a .env committed by accident. Git in particular does not forget — a key pushed once lives in the history until the history itself is rewritten.

The alternative is identity-based authentication, and the mechanism is worth understanding rather than memorizing. You sign in once with az login; that sign-in obeys every organizational control, because it is the same sign-in as everything else. Your machine then holds a refreshable proof of who you are. When your program needs to call a service, the SDK exchanges that proof for a short-lived access token — typically valid about an hour — scoped to that specific service, and attaches it to the request. Nothing long-lived is ever stored in your project, so there is nothing to leak; access is granted by role assignments that an administrator can see and revoke centrally; and the audit trail names a person.

Why we install a CLI: it is the piece that makes keyless authentication possible on a developer's own machine.

And this is precisely why the CLI is not optional for us. On your laptop, the SDK cannot invent an identity — it looks for one. DefaultAzureCredential, the class our code uses, walks an ordered chain of sources and takes the first that answers: environment variables, a managed identity (when running inside Azure), the Visual Studio Code sign-in, the Azure CLI's sign-in, the Azure PowerShell sign-in. Locally, az login is what puts a link in that chain. In Session 6, when the same code runs in a container in Azure, the chain finds a managed identity instead and the code does not change by a single character. That is the payoff: one authentication strategy from laptop to production.

So when is a key legitimate?

When there is no identity to use: a container running outside Azure, a partner system that supports nothing else, a five-minute experiment. Then the rules are absolute — the key lives in an environment variable or a secrets vault, never in source; the file holding it is git-ignored; and it is rotated on a schedule. Our own course backend supports both lanes deliberately, so you can see the difference in one codebase.

What "installing" actually does

Two installations happen in Lab A, and they are different in kind. Installing the Azure CLI places a program on your computer and adds its location to your PATH — the list of folders your terminal searches when you type a command. That is the whole mystery behind the classic first error, "'az' is not recognized": the program exists, but the terminal you opened before installing it does not yet know where to look. Closing and reopening the terminal solves it, because a new terminal reads the updated PATH.

Installing the SDK is narrower: it downloads Python packages into a virtual environment — a private folder holding this project's dependencies, isolated from your system Python and from every other project. That isolation is why two projects can require different versions of the same library without a fight, and why deleting a project folder removes its dependencies with it. Whether you use pip inside a venv or uv (the faster tool our course backend uses), the concept is identical.

Step 4 — prove the whole chain works (≈8′)

This script does something deliberately small and enormously informative: it asks the identity library for a token, without calling any model. If it prints a token length and an expiry, then your sign-in, your CLI, your Python environment and the identity chain are all correct — and every later failure is about permissions or endpoints, not about your machine.

whoami.py 
from azure.identity import DefaultAzureCredential
from datetime import datetime, timezone

credential = DefaultAzureCredential()

# ask for a token scoped to Azure AI services (the data plane we will call later)
token = credential.get_token("https://cognitiveservices.azure.com/.default")

expires = datetime.fromtimestamp(token.expires_on, tz=timezone.utc)
print("token acquired :", len(token.token), "characters")
print("valid until    :", expires.isoformat(), "(UTC)")
print("credential type:", type(credential).__name__)
run it 
python whoami.py

Expected: three lines, the middle one roughly an hour in the future. Look at that expiry and connect it to the theory: this is the short-lived credential that replaces a permanent key, minted on demand from your sign-in and discarded when it ages out.

Resources, resource groups & why geography is engineering

Everything you create in Azure — a Foundry account, a database, a container app, a storage account, even a role assignment — is a resource: a manageable object with a type, a location, a set of properties, and a unique identifier. That identifier is not a random string; it is a path that spells out exactly where the object lives in the platform's hierarchy, and learning to read it is one of the highest-value five minutes in this course.

You will meet this string constantly — in role assignments, in scripts, in error messages, in the portal's own URLs. Whenever something is "not found", read the ID in the error from left to right: wrong subscription, wrong resource group and wrong name are three different problems with three different fixes.

What a resource group really is

A resource group is often introduced as "a folder for resources", which is true enough to be misleading. It is a container with four concrete semantics, and knowing them changes how you organize work:

SemanticWhat it doesPractical consequence
LifecycleDeleting the group deletes every resource inside itGroup things that live and die together — a per-course group can be removed in one command when the course ends
PermissionsRole assignments made on the group are inherited by every resource in itGrant a team access once instead of resource by resource
PolicyGovernance rules applied to the group apply to everything within"Only these regions", "every resource must be tagged" — enforced automatically
Organization & costA natural unit for tagging and for filtering the billCost analysis per group answers "what does this project cost?" without arithmetic

Equally important is what a resource group is not. It is not a network boundary — two resources in the same group are not automatically able to reach each other privately, and two in different groups are not isolated. It is not a security boundary in itself; permissions flow from role assignments, wherever they are made. And it is not a billing account: costs are attributed to the subscription, with the group serving only as a convenient filter.

One subtlety that confuses newcomers: a resource group itself has a location, but that location only stores the group's own metadata. Resources inside it can live in entirely different regions. A group in West Europe holding a model deployment in Sweden Central is perfectly legal — and, more importantly, the deployment's region is the one that determines latency, residency, availability and price.

Geography is not a formality

When the portal asks for a region, it is asking which physical buildings will hold your data and run your computation. Five consequences follow, and you should be able to state all five when someone asks why you chose Sweden Central over East US.

Latency is physics, not configuration. Light in fibre covers roughly 200 km per millisecond, and a request must travel there and back — so every 1000 km of distance costs about 10 ms of round trip before any processing happens, and real networks with their routers and hops do worse. Bucharest to a European datacenter is a few tens of milliseconds; Bucharest to the American west coast is closer to 180. For a chat application streaming tokens, that difference is the gap between "instant" and "sluggish".

Data residency and sovereignty is where banking becomes categorical. Regions are grouped into geographies — Europe, United States, and so on — and a geography is a legal boundary, defining which jurisdiction's law applies to data at rest. GDPR obligations, national banking regulations and internal policy routinely require that customer data never leave a specific geography. This is why "the model is slightly better in that other region" is an argument that loses, every time, to "our data may not go there".

Model availability differs per region, and this surprises almost everyone at least once. Not every model in the catalog exists everywhere: new models appear in a handful of regions first and spread later. If a model you want is absent from the region you picked, you either pick another region or use a deployment type that routes globally. Check before you commit — a resource cannot be moved between regions after creation; recreating it is the only remedy.

Quota is per subscription, per region, per model. Your tokens-per-minute allowance in Sweden Central is unrelated to your allowance in West Europe. That is occasionally useful — a second region can be a capacity strategy — and occasionally the explanation for a mysterious refusal to deploy.

Finally, price varies by region for the same service, as energy, land and local demand differ. The variation is usually modest, but at production volumes it is real money, and it belongs in the decision alongside the other four.

For today's lab

Choose a European region — Sweden Central or West Europe are good defaults for this course: close enough for good latency, inside the EU geography, and well supplied with models. Note your choice; you will need to use the same one consistently in Lab B.

Naming, so that future-you can navigate

Resource names appear in URLs, IDs, logs and bills forever, and many cannot be changed after creation. Conventions cost nothing now and save hours later; a widely used pattern is <type-abbreviation>-<workload>-<environment> — rg-ai-course, rg-libra-assist-prod. Two constraints to remember: some resource names must be globally unique across all of Azure (anything that becomes a public hostname, including your Foundry account, whose name ends up inside <name>.services.ai.azure.com), and most disallow spaces and exotic characters. If a name is rejected as taken, someone else in the world holds it — add a suffix.

Two portals: portal.azure.com vs ai.azure.com

Both are websites, both show your Foundry resource, and beginners reasonably wonder whether one is simply a newer version of the other. It is not. They are two lenses on the same objects, built for two different jobs, and the fastest way to internalize the difference is: portal.azure.com manages the resource; ai.azure.com uses it.

The Azure portal is the universal interface to the control plane. Every Azure service appears there under the same conventions: an Overview blade, Access control (IAM) for role assignments, Networking, Monitoring, Cost, Tags, Diagnostic settings, Keys. It is the surface where an administrator works — where you create the resource in the first place, decide who may touch it, connect it to a virtual network, set a budget alert, or read the audit log. Its vocabulary is subscriptions, resource groups, roles and policies.

The Foundry portal at ai.azure.com is a purpose-built workbench for the people building AI applications on top of that resource. Its vocabulary is projects, models, deployments, agents, knowledge, evaluations and guardrails. You cannot assign an Azure role there or configure a firewall; you can browse a model catalog, deploy a model in three clicks, chat with it in a playground, attach a knowledge source, define an agent and run an evaluation — none of which the Azure portal exposes in a usable way.

Four that deserve more than a table row

Agents are the largest conceptual step. Everything you have built so far is you orchestrating: your code calls the model, reads the answer, decides what to do next. An agent inverts that — you give the model instructions and a set of tools, and the platform runs the loop: the model decides which tool to call, the runtime executes it, feeds the result back, and repeats until the task is done. The Agent Service hosts that loop, keeps the conversation in a thread, and records each execution as a run you can inspect. The engineering shifts from writing logic to defining capabilities and boundaries — which is exactly why Guardrails and approval gates matter more as autonomy grows.

Fine-tune is the most frequently misused section, so learn its decision rule now: reach for it last. If the model does not know your facts, the answer is grounding (Knowledge), not fine-tuning — facts change, weights do not. If it does not follow your format or tone, the answer is usually a better prompt with examples. Fine-tuning earns its cost when you need a consistent behaviour or style that prompting cannot reliably produce, or when you want a smaller, cheaper model to imitate a larger one on a narrow task. It requires curated training data, produces a model you must maintain, and starts the whole evaluation question again from scratch.

Knowledge and Memory are easy to confuse and completely different. Knowledge is shared, factual, and retrieved — a corpus of documents the model consults when a question touches them. Memory is personal, conversational, and carried — the fact that this particular user prefers English, or that we discussed their mortgage last week. Knowledge changes when the bank publishes a new policy; memory changes when a person tells the assistant something. In banking they also differ in governance: knowledge is content management, memory is personal data with retention obligations attached.

Guardrails is where the platform stops being neutral. Every call through your deployment passes classifiers that score prompts and completions for categories of harm; you configure the severity threshold at which each is blocked, add blocklists for terms your institution will not tolerate, and enable shields against prompt-injection attempts where retrieved content might carry instructions. Two things to internalize: filtering happens server-side, so your application must handle a filtered response as a normal outcome rather than an exception; and defaults are a starting point — a bank tunes them, documents the tuning, and treats that document as part of its control framework.

One key for everything? Wiring each surface from code

Now the question that this whole morning has been building toward, and the one most beginners get wrong: can I use the same API key for all of it? The short answer is no — and once you see why, you will stop wanting to.

Recall the fork in the first diagram. Azure is not one endpoint with one credential; it is a control plane plus many independent data planes. Creating a resource is ARM. Calling a model is your Foundry resource's endpoint. Querying a search index is Azure AI Search's endpoint. Reading a blob is the storage account's endpoint. Each of those has its own hostname, its own SDK package, its own notion of permission — and each issues its own keys, which are valid nowhere else. So a "key for everything" cannot exist: with key-based authentication you inevitably accumulate one secret per service, each needing storage, rotation and an owner.

Identity solves precisely this. You have one identity; each service is granted to it by a role assignment. Your code constructs one credential object and hands the same object to every client. Each client asks for a token scoped to its own service — that is the credential_scopes argument you have already seen in our backend — and receives one, provided a role says it may. Nothing is stored, everything is attributable, and access is revoked centrally by removing a role rather than by hunting down copies of a string.

Services vs agents — two different words for two different things

In the Foundry menu you met both Services and Agents, and the portal offers to attach a service to an agent — which makes them sound like variants of one idea. They are not, and confusing them produces bad architectures.

A service is a capability: a specialized, deterministic-ish function exposed as an API. Speech converts audio to text. Translator converts one language to another. Document Intelligence extracts fields from a PDF. Content Understanding pulls structure out of mixed media. Each does one thing, does it without reasoning about your business, and returns the same kind of output every time. You call it directly, from any code, whether or not any language model is involved. It is a component.

An agent is a decision-maker: a language model plus instructions, plus a set of capabilities it is permitted to invoke, running in a loop until a task is complete. Its defining property is that it chooses — which tool to call, with what arguments, when it has enough to answer. You do not tell it "transcribe this then translate it"; you tell it what it is for, hand it Speech and Translator, and it works out the sequence.

Where pure vector search starts to hurt

Now the honest part. Vector similarity is excellent at paraphrase and terrible at precision. Ask for an exact account number, a product code, an IBAN or a specific date and semantic search will happily return something that looks similar — because "IBAN RO49 AAAA 1B31" and "IBAN RO12 BBBB 9C22" are extremely close in embedding space, and completely different in fact. Keyword search has the opposite profile: exact where vectors are vague, useless where wording differs.

What Azure AI Search is

Azure AI Search is a managed search engine — a separate Azure resource, with its own endpoint, its own keys, its own roles — designed for exactly this problem. Three of its capabilities matter most for our purposes.

Hybrid search runs a keyword query and a vector query against the same index simultaneously and fuses the two result lists into one ranking (the standard technique is reciprocal rank fusion: a document that appears high in either list rises, a document high in both wins). This single feature removes the precision weakness described above without giving up paraphrase matching. In published comparisons hybrid retrieval consistently beats either method alone, and it is the default you should reach for.

Semantic ranking takes the top results of that fused list and re-scores them with a language model trained for relevance, then optionally returns extractive captions and a direct answer span. It is a second, smarter pass over a small candidate set — expensive per document, cheap because there are few.

Security trimming is the one a bank cannot do without. Each indexed document carries the identities or groups permitted to see it; every query is issued with the caller's identity, and the engine filters before ranking. The alternative — retrieving freely and hoping the model does not quote what the user may not read — is not an access-control model, it is a hope. Retrieval is where confidentiality is enforced in a RAG system, and the enforcement must happen in the search layer.

  "refuse_when_unsupported": true
}

The application composes that JSON into the system prompt at call time — instructions, then the style rules as a list, then the grounding clauses if retrieval supplied context. You can see the result without guessing: GET /agents/lyrical returns the exact system prompt the file produces, both grounded and ungrounded.

app/agents/persona.py — JSON becomes a prompt 
def system_prompt(self, *, grounded: bool) -> str:
    parts = [self.instructions.strip()]

    if self.style_rules:
        rules = "\n".join(f"- {r}" for r in self.style_rules)
        parts.append(f"Style rules you must follow:\n{rules}")

    if grounded:
        grounding = ["You are given CONTEXT passages retrieved from the bank's own documents.",
                     "Base your answer on those passages."]
        if self.require_citations:
            grounding.append("Cite the passages you use as [1], [2], … .")
        if self.refuse_when_unsupported:
            grounding.append("If the passages do not contain what is needed, say so explicitly "
                             "instead of inventing an answer.")
        parts.append(" ".join(grounding))

    return "\n\n".join(parts)

def run(persona, question, chunks=None, temperature=None) -> AgentReply:
    chunks = chunks or []
    system = persona.system_prompt(grounded=bool(chunks))
    user = build_user_prompt(question, chunks)

    temp = temperature if temperature is not None else (
        persona.temperature if persona.temperature is not None else settings.llm_temperature)

    result = get_llm().chat(system=system, user=user,
                            temperature=temp, max_tokens=persona.max_tokens or settings.llm_max_tokens)

                      system_prompt=system, prompt_sent=user, ...)

Notice the precedence rule in that temperature line — request value, then persona file, then environment default. Small, but it is the pattern every configurable system uses, and students should see it stated once.

The takeaway to say out loud

The persona file changed the product's personality; the Python did not change at all. That separation is why prompts live in version-controlled data files in serious projects — a domain expert can propose a change, a reviewer can read the diff, and nobody redeploys code to adjust tone.

Three ways a program proves who it is

The container default is a convenience, not a limit — and the distinction is worth making explicitly, because "keys don't work in Docker, so use a key" is precisely the confusion this course exists to remove. A program can hold an Entra identity in three ways, and they form a clear order of preference:

Managed identity Running in Azure. The platform issues the token; there is no secret anywhere to store, leak or rotate. Session 6 uses this.
→
Service principal An application identity with an id and a secret, read from the environment. What a container outside Azure uses — including on your laptop.
→
API key Not an identity at all: a bearer secret with no expiry, no attribution, no scope. Last resort.

Preference order. DefaultAzureCredential reads all three from the same chain — the code never changes, only where it runs.

The Agent Service accepts only Microsoft Entra authentication, and the API container runs with a key — so it cannot ask, and the honest answer is unknown rather than "not deployed". A detail worth pointing out on screen

In docker-compose.yml the API service sets AZURE_AI_AUTH=key while your .env keeps identity. Creating a resource makes you its administrator, but calling models is a data-plane action that needs a data-plane role. This is the single most common cause of "I created it and my code still gets 403".

Conclusions

What today changed

You began the morning as a user of someone else's environment and end it as the owner of your own. Along the way the platform stopped being a website and became a system you can address three ways — by clicking, by typing, and from your own program — all three producing the same authenticated HTTP calls against a control plane that manages resources and data planes that do the work. That distinction is not academic: it is why there is no single key for everything, why one identity with several role assignments is the professional pattern, and why we installed a CLI at all.

You can now read any Azure resource ID and say exactly where the object lives; you can justify a region on latency, residency, availability, quota and price; you know which portal owns which task and what every section of the Foundry menu is for. And you have proof rather than belief: a resource group you created, models you deployed, a role you assigned, and the course application answering questions through your own endpoint with no secret in sight. Next session builds directly on this — when we ground the assistant in real documents, you will be adding a service to your environment, with a role assignment rather than another key.

Takeaways

If you remember six things

1. Portal, CLI and SDK are three clients of one REST platform — explore by clicking, deliver by scripting, run from code.

2. Control plane manages resources; data planes do the work. They authenticate differently — that is the whole "one key?" answer.

3. A key is a permanent bearer secret with no identity, no scope and no expiry. A token is short-lived, attributable and revocable.

4. Resource groups are lifecycle, permission, policy and cost containers — not network or trust boundaries.

5. Region decides latency, residency, model availability, quota and price — and cannot be changed after creation.

6. One DefaultAzureCredential, many clients, one role assignment per service. Adding a capability means adding a role, not a secret.
